# Q-FLOW28-PF Team A — TRNG/DRBG control + zeroisation starter

## Scope and source of truth
Built against the uploaded `QFLOW28PF_TeamA_Control_Security_Transaction` §5 and `QFLOW28PF_COMMON_REGISTER_MAP_v1.0`.

Frozen architectural requirements represented here:
- TRNG pipeline: entropy source(s) -> startup and continuous health testing -> conditioning -> DRBG -> consumers.
- Initial target is two entropy sources; exact circuits depend on process/IP/security analysis.
- Health failure must block random output.
- Shared zeroisation order is `abort -> zeroize -> invalidate -> record`, triggered by context-clear or fault/tamper/fatal-integrity events.
- Completion is bounded by each participant's `zeroize_busy`; do not assume a fixed scrub latency.
- Register offsets: `TRNG_CTRL=0x6000`, `TRNG_STATUS=0x6004`, `TRNG_HEALTH=0x6008`, `DRBG_RESEED_COUNT=0x600C`.

## Files
- `rtl/qf_zeroize_ctrl.sv`: shared four-stage zeroisation sequencer.
- `rtl/qf_trng_drbg_ctrl.sv`: control/status wrapper around external entropy health, conditioner and approved DRBG core.
- `rtl/qf_trng_zeroize_integration.sv`: thin integration shell.
- `tb/tb_qf_zeroize_ctrl.sv`: directed command-clear and fault-trigger test with busy-handshake participant models.
- `tb/tb_qf_trng_drbg_ctrl.sv`: directed health-gating and fault test.

## Explicitly proposed / unresolved choices
1. Zeroisation participant handshake: controller emits one-cycle request pulses. Each participant must latch its request, assert its `zeroize_busy` within the following cycle, hold busy while scrubbing, and deassert only after completion. The controller waits until it has observed every participant busy at least once and all busy signals return low. This is a proposed handshake because the architecture says to use `zeroize_busy`, but does not fully define pulse/acceptance timing in the supplied section.
2. Priority: the implementation gives security fault/tamper/fatal-integrity and context-clear the same trigger path; fault/tamper/fatal-integrity latches `fault_latched`. The Team A contract labels the detailed six-level priority table as recovered/proposed and pending security review. Do not claim this RTL closes security review.
3. Seed width is 256 bits in this control wrapper as a placeholder. The supplied TRNG register map does not freeze a DRBG seed width or algorithm. Replace it with the approved DRBG standard/IP interface before integration.
4. Health checks are external inputs. The RTL does not invent a repetition-count/adaptive-proportion threshold. Select source-specific tests and thresholds with entropy-source designers.
5. Conditioning and DRBG cryptographic implementation are external. `drbg_random_i` must come from an approved DRBG implementation; do not replace it with LFSR/xorshift and call it cryptographic randomness.
6. Sticky health fault is reset-only in this starter because the supplied register map does not define a software recovery/clear mechanism. Add only after security review defines recovery semantics.
7. `policy_allow_i` is a local integration gate, not a new host-visible register or frozen Team A signal.

## Integration checklist
- Synchronize health/fault signals to `clk_i` at the source boundary; `health_fault_i` is assumed synchronous here.
- Connect physical entropy source(s) to source-specific health-test IP; use two sources as the initial target, not a claim that two independent sources are mandatory.
- Connect conditioned seed valid/data and DRBG seed/generate/reseed/zeroize ports to the selected, reviewed DRBG IP.
- Connect all zeroization participants: Key Vault, Context Manager, Secure Scratchpad, and DRBG working state. Verify that each latches the request pulse and provides a valid busy interval.
- Connect `invalidate_req_o` to result/context invalidation; connect `event_record_o` to the security event recorder and update `ZEROIZE_COUNT` only when the system-level definition says zeroization completed.
- Integrate register reads/writes in the existing APB register file; these modules do not implement the full APB slave.
- Map `TRNG_CTRL[0]` enable and `TRNG_CTRL[1]` write-one-to-start reseed semantics in the register wrapper. The input `reseed_request_i` is expected to be a one-cycle pulse generated by that wrapper.
- Preserve the register map field definitions: `TRNG_STATUS[0]=ready`, `[1]=drbg_busy`, `[2]=health_pass`, `[3]=health_fault`, `[4]=reseed_required`; `TRNG_HEALTH[0]=health_test_pass`, `[1]=health_test_running`, `[2]=health_fault_sticky`.

## Verification
With Verilator installed, from this directory:

```sh
verilator --binary --timing --top-module tb_qf_zeroize_ctrl rtl/qf_zeroize_ctrl.sv tb/tb_qf_zeroize_ctrl.sv
./obj_dir/Vtb_qf_zeroize_ctrl

verilator --binary --timing --top-module tb_qf_trng_drbg_ctrl rtl/qf_trng_drbg_ctrl.sv tb/tb_qf_trng_drbg_ctrl.sv
./obj_dir/Vtb_qf_trng_drbg_ctrl
```

Use a separate build directory for each test or remove `obj_dir` between runs. Run lint before integration. Some simulators may warn about the compact enum/case style; treat warnings according to your project lint policy.

## Known prototype limitation to fix first
The wrapper's `reseed_required` currently asserts before the first successful reseed and whenever health input is low; the approved DRBG policy may require a more explicit reseed counter/threshold. This is intentionally conservative starter behavior, not a frozen specification. Before tapeout, the design needs approved DRBG standard, reseed interval, entropy assessment, health-test thresholds, zeroize priority sign-off, and physical implementation review.
